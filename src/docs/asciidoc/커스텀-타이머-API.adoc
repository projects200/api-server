== 오프라인 동기화 공통 계약

* POST의 `createRequestId`는 선택 UUID입니다. `editedAt`은 선택 정수이며 UTC Unix epoch 밀리초(0 이상)입니다.
  `editedAt`만 보내면 `400 INVALID_INPUT_VALUE`입니다. `createRequestId`만 보내면 서버 현재 시각을 사용합니다.
* PATCH/PUT 및 DELETE의 `editId`(UUID)와 `editedAt`은 둘 다 보내거나 둘 다 생략합니다.
  일부만 보내거나 음수 시각을 보내면 `400 INVALID_INPUT_VALUE`입니다.
  DELETE는 선택 JSON 본문 `{"editId":"UUID","editedAt":1792407600123}`을 받으며, 본문 없음 또는 `{}`는 기존 삭제 방식입니다.
* 메타데이터가 없는 기존 요청은 동작을 유지합니다. 기존 수정/삭제 응답의 `data`는 `null`입니다.
  동기화 수정/삭제 응답의 `data`는 `{"updatedAt":"2026-10-19T11:00:00.123"}`입니다.
  POST 응답에는 기존 `customTimerId`와 `updatedAt`을 반환합니다.
  목록/상세 응답의 타이머에도 `updatedAt`을 반환합니다. `editedAt`과 삭제된 타이머는 조회 응답에 노출하지 않습니다.
* `updatedAt`은 서버의 기존 ISO 로컬 날짜·시간 형식을 유지하며 저장과 응답 모두 밀리초 정밀도입니다.
  `editedAt`은 수정 순서 비교용 기기 시각이고, `updatedAt`은 서버 응답 시각이므로 서로 바꿔 쓰지 않습니다.
  업그레이드 이전 행의 `editedAt`은 NULL로 유지하고 기존 서버 `updatedAt`을 JVM 시스템 시간대로 해석하여 비교합니다.
* 생성 요청 ID는 회원별로 심플/커스텀 타이머 전체에서 유일합니다.
  같은 회원·ID·종류의 재요청은 이후 수정·삭제가 발생해도 최초 ID와 최초 `updatedAt`을 반환합니다.
  같은 생성 ID를 다른 타이머 종류에 사용하면 `400 TIMER_REQUEST_ID_REUSED`입니다.
* 편집 요청 ID는 `(회원, 타이머 종류, 타이머 ID, editId)`별로 유일합니다.
  같은 키·동작의 재요청은 현재 상태를 다시 변경하지 않고 최초 성공의 `updatedAt`을 반환합니다.
  같은 키를 다른 동작(수정/이름 변경/전체 교체/삭제)에 사용하면 `400 TIMER_REQUEST_ID_REUSED`입니다.
  같은 ID는 같은 요청을 뜻하며 본문이 달라도 새 요청이 되지 않습니다.
* 서버는 성공 영수증을 삭제·충돌 검사보다 먼저 조회합니다.
  새 편집의 시각이 서버보다 엄격히 오래된 경우에만 `409 TIMER_EDIT_CONFLICT`이며 같은 시각은 허용합니다.
  이 오류는 `succeed:false`, `code:TIMER_EDIT_CONFLICT`와 현재 이름 및 활성 스텝을 포함한 전체 커스텀 타이머 상세를 `data`에 반환합니다.
  이미 삭제된 본인 타이머의 새 수정은 시각과 무관하게 `410 TIMER_DELETED`입니다.
  이미 삭제된 본인 타이머의 새 동기화 삭제는 삭제 시 기록한 `updatedAt`을 반환하며 성공합니다.
  존재하지 않거나 다른 회원의 타이머는 기존 404를 유지하며, 기존 방식으로 삭제된 타이머를 다시 변경해도 404입니다.
  본인이 삭제한 커스텀 타이머의 상세 조회도 404입니다.
* 서버는 모든 타이머 쓰기를 같은 회원 행 잠금으로 직렬화하며 부모·스텝 변경과 성공 영수증을 한 트랜잭션에 저장합니다.
  실패한 변경은 성공 영수증을 남기지 않습니다. 영수증에는 자동 만료나 정리 작업이 없습니다.
  타이머 삭제·회원 소프트 삭제로 영수증을 지우지 않으며 회원 물리 삭제 시에만 FK CASCADE로 삭제합니다.

== 서버 배포 순서

. 기존 DB에는 `documents/Undabang SQL/timer_sync_upgrade.sql`을 먼저 적용합니다.
  NULL 허용 `edited_at`, 두 영수증 테이블과 유일 제약을 먼저 준비합니다.
  부모 타이머에서는 `updated_at`만 DATETIME(3)으로 변경하며 생성/삭제 시각 컬럼은 유지합니다.
  이 스크립트는 기존 행을 지우거나 기기 시각을 추측하여 채우지 않습니다. 부모 `updated_at`의 자동 ON UPDATE는 제거합니다.
  MySQL DDL은 암묵적으로 커밋되므로 각 문장의 적용 상태를 확인하고, 완료된 추가 마이그레이션을 통째로 재실행하지 않습니다.
. #574와 #575를 포함한 서버를 같은 배포로 반영합니다. 애플리케이션이 타임스탬프를 직접 관리합니다.
. 두 서버 API가 준비된 뒤 Android #588을 배포합니다.

WARNING: `Undabang Database DDL.sql`은 DROP TABLE을 포함한 신규 설치용입니다. 기존 DB 업그레이드에 사용하지 않습니다.
